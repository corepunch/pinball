# Инструменты проектирования и проверки столов

Анализатор использует настоящие `PBPhysicsWorld` и `PBGame`, без графического движка. Python проверяет сценарии, запускает native-процесс и строит отчёты. Требуется Mac с Xcode command-line tools; на Linux работают проверки формата и отчётов, но симуляция не подменяется другой физикой.

## Быстрый старт

```sh
make analysis TABLE=aurora
open Build/Analysis/aurora/index.html
make analysis-test
```

Эквивалентная команда:

```sh
python3 tools/analyze_table.py GameData/Tables/aurora.json \
  --suite GameData/Analysis/authoring.json --workers 4 \
  --out Build/Analysis/aurora
```

Первый запуск компилирует native runner с `-O3`; следующие используют кэш, ключ которого зависит от содержимого исходников Core и анализатора. Менять JSON можно без компиляции. Native-процесс можно оставить запущенным:

```sh
python3 tools/analyze_table.py --serve
```

В stdin — по одному JSON-запросу на строку:

```json
{"table":"GameData/Tables/aurora.json","suite":"GameData/Analysis/authoring.json","out":"Build/Analysis/aurora","workers":4,"grid":64}
```

На каждом запросе JSON поля перечитывается, поэтому старые коллайдеры не остаются после изменения геометрии. Независимые испытания выполняются параллельно, результаты сохраняются в исходном порядке. Входные события квантуются до 60 Гц — того же порядка частоты, что и текущий ввод игры. Физика fixture-испытания идёт точными шагами 1/960 с, без увеличения dt и без ожидания кадров.

## Что получаем

Границы анализа и высота карт следуют общей проекции эталонного телефона 402×874 (safe areas 59/34).
Полноэкранное поле выше номинальных 1.9 единиц XML: законный проход над верхними дорожками
не считается `invalid`. Физика и данные стола от этого не меняются.

- `index.html`: самостоятельный отчёт, таблицы исходов, карты и траектории.
- `playfield-visits.svg`, `ramp-visits.svg`: посещения каждой клетки, максимум один раз за испытание.
- `playfield-dwell.svg`, `ramp-dwell.svg`: время в клетке; в подсказке также средняя скорость. Штрихи показывают направление.
- `trajectories.svg`: первые 64 испытания, цвет обозначает исход. Линии разных шаров, слоёв и телепортаций не соединяются.
- `report.json`: исходы по сценарию, количество событий по ID каждого устройства, тайминги, длительность native-прогона и steps/s.
- `replay.json`: точный запрос, seed, положение и скорость подачи, управляющие события; при обычном CLI-запуске также SHA256 таблицы и suite.
- `runs.json`: полный набор событий с tick, ID и номером шара, трассы и исходные карты.

Для A/B:

```sh
python3 tools/analyze_table.py GameData/Tables/aurora.json \
  --suite GameData/Analysis/authoring.json --out Build/Analysis/after \
  --compare Build/Analysis/before/report.json
```

Сравнение сохраняется в JSON. Использовать одинаковые сценарии, seed, горизонты и версию физики. Эта команда не делает статистически независимыми соседние тайминги одного удара.

Проверить формат без симуляции:

```sh
python3 tools/analyze_table.py GameData/Tables/aurora.json \
  --suite GameData/Analysis/authoring.json --check
```

## Как добавить испытание

Создать JSON с массивом `scenarios`. Минимальный локальный сценарий:

```json
{
  "scenarios": [{
    "id": "left-ramp-probe",
    "mode": "fixture",
    "position": [0.37, 0.29],
    "velocity": [0, -0.8],
    "seconds": 8,
    "seeds": [17, 41],
    "controls": [{"at": 0.05, "left": true}, {"at": 0.4, "left": false}],
    "sweep": {"control": 0, "at": [0, 0.016666667, 0.033333333, 0.05, 0.066666667]},
    "expect": [
      {"event": "flipperContact", "element": "flipperL"},
      {"event": "rampEnter", "element": "rampR"},
      {"event": "rampComplete", "element": "rampR"}
    ],
    "returnBox": [0.15, 0.18, 0.45, 0.5]
  }]
}
```

Это пример исследовательской подачи, а не доказанный удачный удар Aurora. Suite `authoring.json` содержит 128 таких проб от двух лопаток. Нулевой успех означает, что нужно исследовать подачу, тайминг и геометрию, а не автоматически ослаблять тест.

`expect` — упорядоченная подпоследовательность событий одного шара. Промежуточные события не запрещены. `success` означает, что вся последовательность найдена до конца наблюдения; `drain`, `stuck`, `invalid` и `timeout` различаются. Технический дефект имеет приоритет над ранее достигнутым успехом. `timeout` означает недостаточность наблюдения, а не обязательно плохой удар. Наблюдение продолжается после успеха для изучения возврата и последующей потери.

`returnBox` регистрирует нисходящую подачу в заданную область после последовательности. Это **не** доказательство, что игрок действительно способен поймать шар или выполнить комбинацию. Для такого доказательства добавить следующий реальный ввод и следующий ожидаемый удар.

Не смешиваются события разных шаров, но в долгом autoplay номера слотов используются повторно после слива. Поэтому длинные маршрутные контракты задавать fixture-сценариями одного шара; autoplay в первой версии предназначен для покрытия, а не доказательства цепочек через несколько жизней.

### Орбита и пространственные маршруты

Между ожидаемыми событиями можно добавить checkpoint:

```json
{"id":"orbit-top","region":[0.15,1.8,0.85,2.15],"layer":"playfield"}
```

Границы нужно выбрать по реальной геометрии своего стола. Задавать отдельные входную, верхнюю и выходную области в нужном порядке. Один `rollover:orbitR` не доказывает полный обход. Регион засчитывается, когда шар оказывается внутри него; следовательно, область не должна включать исходную подачу. Слишком широкие/перекрывающиеся области ослабляют контракт.

Для проверки состояний fixture можно задать `magnets`, `kickbacks`, `dropsDown` как списки ID. В `controls` можно добавить `{"at":1.2,"eject":"scoop"}`. Штатными программными таймерами и scoring занимается autoplay через `PBGame`; fixture проверяет механику, поэтому выброс saucer задаётся явно.

`mode: autoplay` включает текущий exploratory-автопилот. Suite `coverage.json` использует четыре seed по пять симуляционных минут; это выборка, а не гарантия достижимости каждым игроком. При `rescue:true` автоматический поиск шара разрешён, но каждый `stuck` остаётся в отчёте. Для fixture rescue по умолчанию выключен, и первое застревание завершает испытание.

### Автоматический допуск сценария

В сценарий можно добавить `"require":{"successesAtLeast":1,"returnsAtLeast":1,"stuckAtMost":0}`. Пороги относятся ко всему пакету этого сценария, включая sweep и seeds. `report.json` содержит `passed`, `failures` и найденные существующим `PBLayoutValidator` пересечения/узкие проходы. При `--strict` невыполненный порог или невалидная физика дают ненулевой exit code после сохранения отчёта. Без `--strict` исследовательская команда сохраняет наблюдения без автоматического отклонения геометрии. Для нового механизма обязательно написать как положительный, так и отрицательный контракт.

## Как выбирать элемент

| Нужное действие | Кандидат | Что проверять до принятия |
|---|---|---|
| Дать повторяемую прицельную комбинацию | Рампа | Окно входа, запас скорости для подъёма, слабый откат, выход и следующий удар |
| Быстро связать стороны поля | Орбита | Коридор, последовательность checkpoints, скорость и касательная выхода |
| Короткая перемена ритма и активные отскоки | Зона pop bumpers | Подача, контакты каждого бампера, ограниченность пребывания, выход |
| Рискованный точный удар | Stand-up target | Отскок после центра/краёв, вероятность потери после промаха |
| Изменяемая группа целей | Drop targets | Каждая цель, геометрия raised/down, полный reset и повторный проход |
| Проходная цель без захвата | Spinner | Импульс поперёк оси, вращение в обе стороны, скорость/награда |
| Остановить шар для режима/lock | Saucer | Захват на разных скоростях, удержание и выброс без мгновенного перезахвата |
| Управляемая пауза/изменение траектории | Magnet | Off/armed/grab/release, длительность, достижимость и визуальная причина |
| Направить движение в одну сторону | Gate | Пропуск вперёд, отскок назад, крайние касания, отсутствие зажима |
| Дать заслуженное спасение | Kickback | Armed/off, однократность, траектория после спасения |
| Передать удар через другой шар | Captive ball | Импульс и цель за ним, удержание в физическом ограждении |
| Добавить удар из другой точки | Верхняя лопатка | Сначала подача к ней, затем собственный достижимый удар |

Элемент выбирается по пробелу в игровом действии, а не по свободному месту. Если две детали выполняют одну роль, новая должна дать отличающийся маршрут, темп или риск. Если мешает существующему коридору, поменять место или отказаться. Необязательно ставить всё на каждом столе.

## Как добавить новый тип элемента в движок

1. Сформулировать действия игрока, вход, состояния, выход и правило награды.
2. Добавить typed definition/JSON parsing, затем физическую реализацию в `App/Core`.
3. Если нужен новый event kind, **добавить его в конец enum**, обновить `PBEventName`, `PBEventElementIdentifier`, `EVENT_GROUPS` анализатора и его Inventory. Существующие numeric значения не менять.
4. Добавить fixture-тесты: положительный случай, близкий промах, выключенное состояние, крайняя скорость, сброс/повторная активация. Сначала механика отдельно, затем достижимость на столе.
5. Добавить правила/счёт/лампы и визуальные состояния. Новый механический event сам по себе не должен случайно выдавать очки.
6. Обновить authoring/import/export Blender, если объект должен редактироваться там. Проверить round-trip.
7. Добавить устройство в настоящий стол, паспорт удара и suite, повторить анализ соседних маршрутов.
8. Выполнить `make test`, `make analysis-test`, визуальный допуск и проверку на iPhone.

`PBMechanismTests` параметризован по ID контактных устройств обоих shipping-столов. Он проверяет их в изоляции. Дополнительные тесты проверяют горизонтальную рампу/откат, повёрнутый спиннер и обратное вращение, направления ворот, выброс saucer, release магнита, импульс captive ball и strict ball-search. Существующий полный autoplay-тест остаётся отдельной проверкой достижимости в собранном поле.

## Ограничения первой версии

- Физический и отчётный benchmark выводится отдельно; пятисекундный бюджет не следует обещать для любого размера suite или любого Mac. Время cold build исключено из native `wallSeconds`, end-to-end CLI выводит отдельно.
- Fixture-heatmap снимается на 960 Гц; autoplay-heatmap — приближённо на 60 Гц. Трасса fixture — 120 Гц, autoplay — 60 Гц. Геометрические проверки узких проходов не заменяются картой.
- Пока нет интеграции heatmap поверх Blender, автоматического размещения деталей, полного snapshot/restore, отмены устаревших запросов и отдельных novice/skilled ботов. В serve запросы выполняются последовательно.
- Два соседних seed без случайных механизмов дадут одинаковый fixture — это нормально; для разнообразия подач создавать отдельные сценарии с разными входными состояниями.
- Карты сейчас агрегируют suite; для чистого анализа одного удара запускать suite с одним сценарием.
- Нет автоматического допуска художественного качества. Проверять реальные программные снимки спрайтового графа (`tools/render_ui_preview.sh`) и устройство по основному руководству.
