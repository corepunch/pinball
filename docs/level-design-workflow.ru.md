# Проектирование пинбольных столов: маршруты, испытания, качество

Дата аудита: 2 ноября 2026. Проверенный снимок `corepunch/pinball`: `9e0907ec18aa43dd85715f8d492652335852c304`.

Это инструкция для автора уровней и техническое задание на инструменты анализа. Сведения о текущем коде отделены от предлагаемых возможностей. Нового анализатора, новых измерений производительности и сертификации визуального качества этот документ не подразумевает.

## 1. Основное правило

Проектировать нужно цепочку **подача к лопатке → прицельный удар → взаимодействие → возврат → следующий удар**, включая последствия промаха. Каждый игровой элемент обязан иметь роль в этой цепочке. Пустое место не является причиной поставить туда бампер.

Whitewood в нашей игре — нейтральный вид поля с настоящей физикой и простыми читаемыми материалами. Сначала добиваемся хорошей игры, затем оформляем её. Никаких отдельных упрощённых законов физики для редактора или тестов.

Процесс опирается на практику физических столов:

- Джон Попадюк описывает путь от основных траекторий и CAD через объёмный макет к нескольким рабочим whitewood-прототипам [S1].
- Пэт Лолор предлагает оценивать темп, сочетание остановок и плавных возвратов, доступность для новичка и поведение шара после промаха [S2].
- Mission Pinball рекомендует проверять линии ударов с учётом размера шара, подачу к верхней лопатке и направление выхода орбиты; бамперной зоне нужны взаимодействующие отскоки и выход [S3].
- При проверке прохода учитывается диаметр шара: реальный коридор для его центра уже видимого проёма. CAD позволяет предварительно проверить входы и выходы [S4].

Все численные бюджеты, профили ботов и форматы отчётов ниже — предложения для нашей игры, а не отраслевые нормативы.

## 2. Что уже реализовано

Проверены определения элементов, физика, правила, построение сцены, JSON двух столов и исходники тестов. Наличие кода не означает, что все состояния правильно выглядят и играются. Исполнение XCTest и SceneKit в этой Linux-среде недоступно.

| Лопатки | Управление и прицельные удары | 2 / 2 | Карта достижимых ударов, окно тайминга, удержание и возвраты |
| Pop bumpers | Серия активных отскоков, смена ритма | 3 / 3 | Каждый бампер отдельно, вход/выход зоны, отсутствие бесконечного фарма |

| Saucer | Захват, пауза, выброс; может участвовать в lock | 1 / 1 | Захват на разных скоростях, выброс, повторный захват, multiball |
| Gates | Одностороннее направление прохода | 3 / 3 | Обе стороны, анимация, отсутствие зажима |

| Rollovers | Проходные датчики и цели дорожек | 8 / 8, включая `orbitR` | Срабатывание каждой дорожки и защита от повторного счёта |

| Лампы / flashers | Объясняют цели и результат | 21 + 3 / 21 + 3 | Состояние правил, читаемость, отсутствие засветки шара |

Количество одинаковое, но это не доказывает одинаковую геометрию. Нельзя оценивать разнообразие уровней только количеством устройств. `GameData/Levels.json` задаёт задания и звёзды; новый campaign level не обязательно является новым физическим столом.

Орбита не отдельный класс устройства: это маршрут из направляющих, ворот и датчиков. В `PBRuleEngine.m` роль определяется префиксом `orbit*`; одно срабатывание `orbitR` приносит награду. Сейчас это не доказательство полного обхода. Нужна отдельная проверка маршрута, не обязательно новый тип физического объекта.

## 3. С чего начинать новый стол

1. Написать короткий замысел: основное удовольствие, характерный удар, темп, целевая сложность. Например: «быстрые перекрёстные возвраты между двумя рампами, короткая бамперная пауза, рискованная цель для multiball».
2. Зафиксировать физический профиль: размер шара, гравитацию, параметры лопаток, отскоки. Не менять их незаметно, чтобы спасти плохую геометрию.
3. Поставить нижний узел: лопатки, центральный слив, inlanes/outlanes, slingshots, запуск. Проверить удержание, чистый слив при бездействии и возврат неудачного запуска.
4. Построить карту ударов от каждой лопатки на почти пустом поле. Зарезервировать коридоры будущих основных ударов.
5. Спроектировать главный маршрут и его возврат. Проверить отдельно попадания и близкие промахи.
6. Добавлять по одному маршруту или тесно связанному узлу. Для бамперной зоны узел из нескольких бамперов и окружающей резины имеет больше смысла, чем изолированное тестирование одной детали.
7. После каждого изменения сравнить результаты с предыдущим принятым вариантом на одном наборе сценариев.
8. Добавить правила и цели, затем оформление. После оформления снова проверить видимость, коллизии и производительность.

Не нужно использовать весь каталог на каждом столе. Новый элемент принимается, если создаёт полезный выбор, маршрут, ритм или награду и не разрушает существующие удары.

## 4. Паспорт каждого удара

До размещения элемента описать:

| Поле | Содержание |
|---|---|
| ID и назначение | Что делает игрок и зачем |
| Исходная подача | Какая лопатка, диапазон входных положений и скоростей |
| Прицеливание | Входной коридор, допустимые тайминги, скорость входа |
| Успех | Последовательность событий, а не только касание датчика |
| Возврат | К какой лопатке/дорожке, в каком диапазоне скорости |
| Следующий ход | С чем можно связать этот удар |
| Промахи | Ранний/поздний, левее/правее, слабее/сильнее |
| Риск и награда | Ожидаемая опасность, очки или прогресс |
| Состояния | Ворота, поднятые/опущенные мишени, магнит, lock |
| Критерии | Минимальное окно успеха и допустимые риски для сложности стола |

Пример замысла, не результат измерения Aurora: «левая лопатка → правая рампа → левая inlane → левая лопатка; успешный проход должен давать возможность следующего удара; слабый вход откатывается на поле без застревания».

Рампа не считается хорошей только потому, что один идеальный шар прошёл её. Нужны устойчивый диапазон реальных входов и осмысленные последствия неудач.

## 5. Как определить место элемента

**Сначала желаемое действие и коридор, затем деталь, затем эксперимент.**

1. Запустить серию подач к левой и правой лопатке с изменением времени нажатия. Получить веер достижимых траекторий.
2. Выбрать область, соответствующую нужному удару. Учитывать скорость и направление, а не только количество посещений.
3. Проверить свободный коридор для центра шара: препятствия мысленно/алгоритмически расширяются на радиус шара плюс запас. Учитывать слой и высоту.
4. Ориентировать вход рампы вдоль подходящего потока. Для орбиты задать выходную касательную, ведущую в нужную дорожку или к лопатке. Не направлять наградной возврат случайно в кончик slingshot.
5. Для мишени проверить отскоки по всему её рабочему фронту. Для бамперов — несколько входов, обмен ударами и выход из зоны. Для верхней лопатки сначала обеспечить подачу к ней.
6. Перебрать ограниченное семейство положений/углов/ширин. Сначала отсеять коллизии и невозможные коридоры, затем проверить настоящей физикой.
7. Сравнить с вариантом без элемента и предыдущим принятым вариантом. Зафиксировать, что улучшилось и какой риск появился.

Нельзя просто поставить цель в самое красное место heatmap: это может быть слив, зона потери контроля или ловушка. И после установки детали распределение траекторий изменится — измерять нужно повторно.

Пустой коридор может быть намеренным пространством для прицеливания. Равномерно заполненная heatmap не является целью дизайна.

## 6. Какие карты строить

| Карта | Что измеряет | От чего защищает |
|---|---|---|
| Посещения | Доля испытаний, прошедших через клетку | Один застрявший шар не создаёт ложную популярность |
| Время | Секунды пребывания свободного шара | Видны замедления и зависания |
| Скорость и направление | Распределение векторов по клеткам | Видны опасные возвраты и ориентация входов |
| Попадания | Число контактов по ID элемента и скорости | Видны недоступные цели и слабые взаимодействия |
| Тайминг удара | Успех в зависимости от подачи и момента нажатия | Один удачный тайминг не маскирует невозможный для человека удар |
| Возвраты | После конкретного удара: куда и как вернулся шар | Проверяется продолжение комбинации |
| Потери | Траектории перед сливом с указанием предыдущего события | Видны опасные промахи и выбросы |
| Разница вариантов | Изменение тех же метрик A/B | Можно оценить конкретную правку |

Карты разделять по источнику удара, направлению, слою и состоянию шара. Ramp layer нельзя смешивать с полем под рампой. Captive ball, ожидание на plunger и штатное удержание в saucer/magnet не включать в карту свободного движения.

Посещение: одна клетка учитывается максимум один раз на испытание. Время: суммировать симуляционное dt, не количество кадров. Для быстрых перемещений отмечать пересечённые отрезком клетки; сетка для изображения может быть реже физического шага, если контакты и пересечения сохраняются точно.

Каждая карта должна показывать число испытаний, длительность, политику управления, seed, масштаб и нормировку. Отчёт «0 потерь из 10» не означает нулевой риск. Для долей показывать доверительный интервал и число независимых сценариев; не считать соседние тайминги независимыми игроками.

## 7. Быстрые автоматические испытания

Предлагаются три режима одного native headless runner, использующего `App/Core`. Это ещё не существующие команды проекта.

### A. Локальный эксперимент после правки

- Несколько сотен коротких испытаний главного/изменённого удара.
- Менять входные состояния и тайминги в объявленном диапазоне, а не телепортировать шар на цель.
- Пример стартового бюджета: 256 испытаний по 8 симуляционных секунд. Это 1 966 080 физических шагов при 960 Гц; скорость выполнения нужно измерить.
- Завершать испытание по событию успеха, сливу, ловушке или горизонту. Незавершённое не считать провалом автоматически: отдельно `timeout/unknown`.
- Записывать карты, окно тайминга, прохождение, возвраты, потери и несколько характерных replay.
- Дешёвый анализ запускать после каждого перемещения; затем проверять соседние маршруты. Общий прогон обязателен перед принятием.

### B. Проверка всего стола

- Directed policy: целится в конкретный объявленный удар; управляет только допустимыми вводами игрока.
- Novice policy: задержки реакции, ошибки тайминга, отсутствие сложных приёмов.
- Skilled policy: целевые последовательности и контроль возвратов.
- Exploratory policy: разнообразное управление для поиска ловушек; существующий автопилот полезен как начальный вариант этого режима.
- Passive policy: без лопаток, чтобы выявлять самоиграющие зоны и остановки.
- Несколько воспроизводимых seed и начальных состояний; отдельные игры, а не один бесконечный сеанс.
- Метрики: длительность шара p10/p50/p90, достижение целей, посещение каждого устройства по ID, завершение маршрутов, контролируемые возвраты, ловушки, доминирующий источник очков, доля игры без участия игрока.

### C. Проверка перед выпуском

- Расширенный фиксированный набор сценариев + отдельный набор, не использовавшийся при настройке.
- Multiball и все изменяющие геометрию/поведение состояния.
- Все оставшиеся существующие тесты.
- Native SceneKit рендеры и видео на целевых размерах экрана; ручная игра и GPU-профиль на iPhone.

Автотесты обязательны. Они находят технические дефекты и измеряют объявленные свойства; сами по себе не доказывают удовольствие от игры или красоту материалов.

## 8. Как уложить обратную связь примерно в пять секунд

Пять секунд — **целевой wall-clock бюджет**, а не пять секунд жизни шара и не обещанная измеренная скорость.

1. Постоянный процесс: не компилировать Xcode-проект и не загружать SceneKit при каждой правке. Загрузить JSON и подготовить неизменяемую геометрию один раз на вариант.
2. Выполнять физику без сна, рендера, звука, UI, Game Center и синхронизации с экраном. Поднять скорость можно снятием ожидания, сохраняя dt, а не увеличением dt.
3. Независимые миры распределять между worker threads. Состояние мира, правила и RNG не разделять; карты объединять после завершения.
4. Сначала локальный пакет, затем полный прогон. Отмена устаревшей задачи при новой правке.
5. На каждом шаге только дешёвые счётчики/массивы; без JSON, PNG и NSLog. Replay хранить выборочно. Сборка отчёта отдельно.
6. Измерять cold/warm время, trials/s, steps/s, память, p50/p95 latency вместе с CPU, числом workers и build configuration. Задать проверяемый performance budget после первого benchmark.

Критическая особенность текущего API: `advanceBy:` ограничивает переданное время до 0.05 с. Вызов `advanceBy:60` не проиграет минуту. `PBGame update:` при этом двигает часы и правила на переданное время. В runner нельзя передавать огромный elapsed: сейчас использовать последовательные вызовы `update:1.0/60.0`, как тесты, или разработать явный согласованный fixed-tick API для мира, правил и ввода. Не удалять защиту live frame loop ради offline ускорения.

Физика работает при 960 Гц, но текущий `PBGame` применяет ввод на границе `update`. Для тонкого поиска тайминга нужен явно зафиксированный input cadence; воспроизведение в игре должно соответствовать runner. Миллисекундная точность ввода, недостижимая на телефоне, не должна делать удар «хорошим».

## 9. Что необходимо добавить к текущим проверкам

Подтверждённые ограничения:

- `PBTableTests` проигрывает 25 симуляционных минут; `validate_level.m` — 40. Это покрытие существующим автопилотом, а не эксперимент с прицельными ударами.
- Часть hits агрегируется по типу (`bumper`, `drop`, `saucer`, `spinner`), поэтому достижение одного устройства не доказывает достижимость каждого. Рампы, rollovers и standups учитываются также по ID.
- RNG мира и автопилота стартует с фиксированных констант; публичной настройки seed в просмотренных API нет. Пересоздание игры само по себе не даёт разнообразия seed.
- `PBEventFlipperUp/Down` означает движение лопатки, а не подтверждённый удар по шару. Для атрибуции нужен отдельный контакт шара с лопаткой, её ID и время.
- `PBEvent` не содержит времени; runner должен добавить номер физического шага и стабильный ID устройства. Общие wall hits сейчас не дают полноценного ID конкретной направляющей.
- Есть автоматическое освобождение застрявшего шара, включая возврат к plunger после нескольких попыток. Это может скрыть дефект поля. Каждый rescue считать отдельным дефектом в строгих тестах, различая его со штатным удержанием.
- Проверка `stuck < drains` слишком слаба для качества отдельного маршрута. В коротких directed-сценариях ожидается ноль незапланированных rescue.
- Тест целей кампании проверяет достижимость и то, что три звезды не выдаются во всех играх. Он не проверяет желаемую кривую сложности по профилям игрока.
- Heatmap, паспортов ударов и анализа возвратов в просмотренном дереве проекта нет.

Нужны snapshot/restore для полного состояния эксперимента: все шары, лопатки, мишени, timers, правила, RNG и накопитель шага. Один и тот же snapshot использовать внутри одного варианта; после изменения геометрии пересоздавать физический мир и воспроизводить общие валидные подачи. Snapshot нельзя без проверки переносить через изменённые коллайдеры. `placeBall:` полезен для fixture-тестов, но не заменяет весь snapshot и не доказывает достижимость подачи в обычной игре.

## 10. Когда принимать элемент

Обязательные технические условия:

- Нет NaN/Inf, выхода за поле, недопустимых пересечений, туннелирования и незапланированных rescue в declared directed-наборе.
- Каждый обязательный удар имеет достижимую в обычной игре подачу и ненулевое устойчивое окно успеха.
- Вход, полный маршрут, выход и награда связаны одной проверяемой последовательностью для конкретного шара. Для multiball события разных шаров не склеиваются.
- У рампы различаются enter, complete и rollback; у орбиты — направление, вход, промежуточная зона и выход с таймаутом.
- Статический зазор проверяется по текущему `table.ballRadius`, коллайдерам и запасу; не копировать устаревшее число 0.05 из README. В проверенных JSON диаметр шара равен 0.06.
- Возврат успешно засчитан только если у игрока была реальная возможность следующего действия, а не просто пересечение произвольной области около лопатки.

Баланс задаётся паспортом стола, не универсальным порогом. Для простого наградного удара нужен широкий рабочий тайминг; для рискованного jackpot допустим меньший, но опасность должна быть читаемой. Измерять `P(drain до следующей возможности контроля | попадание)` отдельно от такого же риска после близкого промаха и от фонового риска. Горизонт наблюдения и его незавершённые случаи указывать явно.

Не оптимизировать единственный score: максимальная длительность шара, максимальные очки и максимальное покрытие поля по отдельности могут дать скучный или самоиграющий стол. Сравнивать несколько критериев и сохранять дизайнерское решение.

## 11. Production quality: отдельный допуск

Текущее состояние: premium-модели, материалы, hit/idle-анимации, предпросмотры и проверки footprints уже предусмотрены проектом. Однако в этом аудите бинарные рендеры не удалось получить, SceneKit не запускался. Ни один элемент не получает отметку «визуально принят» только по исходникам.

Зоны внимания по коду: saucer имеет видимую окантовку; kickback использует модель `stud` или цилиндр; для магнита и captive-ball нужна проверка понятного отдельного визуального обозначения. Это поводы для визуальной проверки, а не доказанные визуальные дефекты. Orbit оценивается как весь читаемый маршрут.

Для каждого типа элемента сделать fixture-сцену с настоящим шаром и реальными событиями. Снять idle → контакт/активация → восстановление, альтернативные состояния и крупный план. Затем проверить тот же объект в загруженном поле на размере телефона.

Критерии:

- Силуэт и назначение узнаваемы, вход и выход видны, шар не теряется на фоне.
- Видимая геометрия соответствует коллизиям; нет контактов с воздухом и прохождения через видимый металл.
- Нет aliasing мелких деталей, мерцания, z-fighting, чёрных shader-пикселей и засветки.
- Рампа имеет непрерывный пол, плавный вход, достаточный внутренний просвет и убедительный выход.
- Мишени различимы в raised/down; gates и spinner двигаются соответственно событию.
- У захвата и магнита понятны состояния ready/held/released; задержка воспринимается как действие устройства.
- Лампы показывают реальное состояние правил; звук и haptics совпадают с ударом.
- Для premium skin нет незамеченного fallback вместо ожидаемой модели. Procedural geometry допустима там, где она намеренно является финальным элементом.
- Native рендер является эталоном материалов; Blender нужен для геометрии. Производительность подтверждается на устройстве.

Доступные сейчас команды на Mac:

```sh
make test
python3 tools/ramp_paths.py
PB_PREVIEW_TABLE=aurora tools/render_preview.sh /tmp/pinball-aurora orbital
PB_PREVIEW_TABLE=meridian tools/render_preview.sh /tmp/pinball-meridian abyss
```

Сверять актуальные параметры с `Art/MODEL_GUIDE.md` и `Art/BLENDER_AUTHORING.md`. В них обнаружено расхождение описаний камеры: 30° и 18°. Для проверок брать реальную константу камеры/экспорт, затем синхронизировать документацию; не принимать скриншоты по противоречивому описанию.

## 12. Порядок реализации инструмента

| Этап | Результат | Критерий готовности |
|---|---|---|
| 1. Воспроизводимость | Native CLI поверх Core, seed, timestamp, ID и flipper-contact telemetry, сценарии ввода | Одинаковые входы повторяют результаты в одной сборке; replay воспроизводит эталон |
| 2. Локальный анализ | Карты траекторий/тайминга/возвратов, отчёт JSON, replay неудач | Хороший маршрут проходит, заведомо закрытый не проходит, ловушка фиксируется до rescue |
| 3. Скорость | Постоянный процесс и независимые workers | Сравнение single/multi-worker совпадает по результатам; latency измерена на заданном Mac |
| 4. Редактор | Результаты поверх Blender/whitewood, отмена устаревших прогонов | Изменение элемента запускает анализ новой ревизии, старый отчёт не маркируется новым |
| 5. Допуск столов | Паспорта Aurora/Meridian, профили игроков, визуальные fixture и device QA | Каждый маршрут подтверждён, ограничения записаны, критерии сложности выполнены |

Первый практический эксперимент: выбрать одну рампу Aurora, измерить веер ударов до правки, её вход/возврат и близкие промахи; затем изменить один параметр и сравнить. Не переставлять сразу весь стол.

## 13. Комплект результата для каждого нового стола

- Короткий замысел и схема маршрутов.
- Паспорт каждого обязательного удара и используемых устройств.
- Whitewood и оформленный вариант из одного источника геометрии.
- Ревизия JSON, версия физики, seed, policy, входные сценарии, build/platform.
- Карты по отдельным ударам, A/B-отчёт, численные результаты и replay провалов.
- Полные регрессионные тесты, visual fixture и native gameplay-видео.
- Записанные результаты проверки на iPhone и дизайнерского playtest.

Без этих свидетельств «расставлено и запускается» не считается завершённым уровнем.
